# Презентация проекта «Трамплин» для конкурса IT-Планета 2026

Этот документ собран по реальной кодовой базе проекта, а не как абстрактная презентация.

Основание для материала:

- проанализированы frontend-маршруты, guards и кабинеты ролей;
- просмотрены основные экраны: главная, каталог, карточка возможности, кабинеты кандидата, работодателя и куратора;
- проверены frontend API-обертки;
- просмотрены backend endpoints, `Program.cs`, `DBContext`, модели статусов и ролевые ограничения;
- учтены реальные ограничения реализации.

Честные ограничения, которые важно учитывать при сборке слайдов:

- модуль жалоб у куратора есть во frontend как UI-заготовка, но полноценный backend workflow для жалоб не найден;
- журнал логов модератора сейчас демонстрационный, опирается на локальный mock-список;
- `tags-system` и `moderator settings` заведены в роутинг как scaffold;
- часть расширенных фильтров и зарплатная сортировка в каталоге показаны как UI-структура, но не как полностью завершенная бизнес-логика;
- runtime-логика приватности кандидата сейчас фактически строится вокруг `links/preferences` в профиле, хотя в БД также есть поле `privacy_settings`.

## 2. Текст по слайдам

### Слайд 1. Трамплин: единая платформа карьерного старта

**Заголовок:** Трамплин: единая платформа карьерного старта

**Тезисы:**

- Трамплин объединяет вакансии, стажировки, менторские программы и карьерные мероприятия в одном продукте.
- Основной сценарий строится вокруг карты и списка возможностей, а не вокруг разрозненных разделов.
- В системе реализованы роли гостя, соискателя, работодателя и куратора.
- Основа доверия платформы: верификация компаний, модерация публикаций и прозрачные статусы откликов.

**Поясняющий текст:**  
Трамплин помогает не просто найти вакансию, а пройти полный маршрут карьерного старта: от поиска возможности до отклика, модерации и обратной связи.

**Что важно для эксперта:**  
Перед ним не набор макетов, а уже собранная продуктовая модель.

**Поясняющий текст:**  
Проект закрывает основные критерии конкурса именно в тех частях, которые эксперт проверяет в первую очередь.

### Слайд 3. Главная страница: карта, список, поиск и фильтрация

**Заголовок:** Главная страница: карта, список, поиск и фильтрация

**Тезисы:**

- Пользователь выбирает город, вводит запрос и сразу получает релевантные возможности.
- Доступно переключение между списком и картой.
- Карта использует цветовую кодировку по типу возможности и карточку предпросмотра точки.
- Поиск и фильтрация работают по названию, компании, городу, тегам и формату.
- В расширенном каталоге реализован отдельный режим большой карты.
- Часть advanced filters и зарплатная сортировка подготовлены как UI-структура и отмечаются как частично реализованные.

**Подписи к интерфейсу:**

- Выбор города
- Поиск
- Фильтры
- Карта / Список
- Легенда типов
- Карточка на карте

**Что важно для эксперта:**  
Карта — это не декоративный элемент, а центральный слой навигации по рынку возможностей.

### Слайд 4. Авторизация, роли и разграничение доступа

**Заголовок:** Авторизация, роли и разграничение доступа

**Тезисы:**

- Соискатель входит по email.
- Работодатель входит по ИНН, а не по email.
- Модератор не регистрируется самостоятельно: доступ открывается только по приглашению.
- Frontend guards проверяют роль и не пускают пользователя в чужой кабинет.
- Backend policies отдельно защищают candidate/company/moderator endpoints.
- JWT-сессия восстанавливается через `/auth/me`, backend умеет читать токен и из cookie.

**Поясняющий текст:**  
Разграничение прав реализовано на двух уровнях: в роутинге SPA и в API.

### Слайд 5. Кабинет соискателя: профиль и приватность

**Заголовок:** Кабинет соискателя: профиль и приватность

**Тезисы:**

- Кандидат настраивает основные данные, навыки, образование, опыт и контакты.
- Отдельный блок приватности управляет видимостью профиля, проектов и активности.
- Отдельно настраивается аудитория для профиля, контактов и сообщений.
- Есть параметр `peerVisibilityDefault` для участия в social-context откликов.
- Публичный профиль кандидата формируется с учетом этих настроек.

**Поясняющий текст:**  
Кандидат управляет не только содержанием профиля, но и тем, кто именно увидит его данные внутри платформы.

**Подписи к интерфейсу:**

- Профиль
- Проекты
- Активность
- Контакты
- Сообщения
- Peer visibility

### Слайд 6. Кабинет соискателя: отклики, статусы и social context

**Заголовок:** Кабинет соискателя: отклики, статусы и social context

**Тезисы:**

- Все отклики собраны в отдельный рабочий раздел с фильтрацией по статусам.
- Статусы жизненного цикла: `submitted`, `reviewing`, `invited`, `accepted`, `rejected`, `withdrawn`.
- Кандидат может отменить отклик или подтвердить участие на нужном этапе.
- Для отклика показываются контакты компании, люди из сети кандидата и видимые peers.
- Возможность можно переслать своему контакту прямо из кабинета.

**Поясняющий текст:**  
Раздел откликов превращает процесс трудоустройства в понятную и отслеживаемую воронку.

**Что важно для эксперта:**  
Это сильное место проекта: отклик связан не только со статусом, но и с контекстом сети.

### Слайд 7. Кабинет работодателя: профиль компании и верификация

**Заголовок:** Кабинет работодателя: профиль компании и верификация

**Тезисы:**

- Работодатель управляет профилем компании и его публичным наполнением.
- Статус компании проходит через `pending / approved / revision / rejected`.
- Для верификации собирается контактное лицо и документ проверки.
- Пока заявка в статусе `pending`, повторная отправка формы блокируется.
- Публичная страница компании доступна только для подтвержденных компаний.
- При изменении ключевых идентификационных данных подтвержденная компания переводится в `revision`.

**Поясняющий текст:**  
Платформа отдельно работает с доверием к работодателю и не выпускает компанию в публичный каталог без проверки.

### Слайд 8. Кабинет работодателя: создание и публикация возможностей

**Заголовок:** Кабинет работодателя: создание и публикация возможностей

**Тезисы:**

- Один редактор поддерживает вакансию, стажировку, мероприятие и менторскую программу.
- Форма включает описание, формат, город, адрес, координаты, теги, контакты и медиа.
- Поддержаны сценарии `сохранить черновик`, `отправить на модерацию`, `архивировать`, `предпросмотр`.
- Для каждого типа работают свои обязательные поля и backend-валидация.
- Backend не позволяет создавать новую возможность без подтвержденной компании.

**Поясняющий текст:**  
Модуль публикации поддерживает и продуктовый UX, и строгую бизнес-валидацию полного жизненного цикла.

### Слайд 9. Кабинет работодателя: работа с откликами

**Заголовок:** Кабинет работодателя: работа с откликами

Кабинет работодателя доводит процесс до принятия решения по кандидату.

### Слайд 10. Кабинет куратора: дашборд и очереди модерации

**Заголовок:** Кабинет куратора: дашборд и очереди модерации

**Тезисы:**

- Куратор видит общее число пользователей, компаний, возможностей и очереди `pending`.

**Заголовок:** Куратор: проверка компаний, возможностей и пользователей

### Слайд 12. Frontend и backend архитектура

**Заголовок:** Frontend и backend архитектура

**Тезисы:**

- Бизнес-логика разделена по доменам: `auth`, `candidate`, `company`, `opportunities`, `moderation`.
- Данные хранятся в `PostgreSQL` через `EF Core 9`.
- Используются интеграции `Yandex Maps`, `Yandex Geocoder` и `Dadata`.

**Поясняющий текст:**  
Архитектура проекта рассчитана на расширение ролей, сценариев и типов карьерных возможностей.

**Поясняющий текст:**  
Структура БД строится вокруг реальных бизнес-состояний, а не вокруг плоских форм.

**Файл:** `src/auth/route-guards.jsx`  
**Почему важно:** подтверждает, что пользователь не остается в чужом кабинете.

```jsx
export function resolveProtectedRouteAccess({
  session,
  allowedRoles,
  guestRedirectTo = routes.auth.login,
}) {
  const normalizedRoles = normalizeAllowedRoles(allowedRoles);

  if (session.status === "idle" || session.status === "loading") {
    return { status: "checking", user: session.user ?? null, redirectTo: null };
  }

  if (session.status === "authenticated" && session.user) {
    const normalizedRole = normalizeAuthRole(session.user.role);
    const hasAccess = normalizedRoles.length === 0 || normalizedRoles.includes(normalizedRole);

    return hasAccess
      ? { status: "allowed", user: session.user, redirectTo: null }
      : { status: "forbidden", user: session.user, redirectTo: getCabinetRouteForRole(normalizedRole) };
  }

  return { status: "unauthenticated", user: null, redirectTo: guestRedirectTo };
}
```

**Что должен увидеть эксперт:**  
Разграничение ролей реализовано в маршрутизации, а не только в скрытии кнопок.

**Коротко для слайда:**

Endpoints подключаются централизованно в `Program.cs`. Авторизация строится на JWT, роли ограничиваются policy-подходом. Бизнес-логика разнесена по файловым модулям и читабельно разделена по доменам.

### 5.4. Как реализовано разграничение прав

**Коротко для слайда:**

- Frontend: guards и role redirects
- Backend: policies `requireCandidateRole`, `requireCompanyRole`, `requireModeratorRole`

**Подробнее для заметок:**

Frontend не позволяет открыть чужой кабинет и отправляет пользователя в релевантный role-home. Backend не полагается на frontend и повторно ограничивает доступ к endpoints по claim role.

### 5.5. Как реализованы статусы

**Коротко для слайда:**

- Компании: `pending / approved / revision / rejected`
- Возможности: `draft / pending / approved / revision / rejected / archived`
- Кандидаты: `pending / approved / revision / rejected`
- Отклики: `submitted / reviewing / invited / accepted / rejected / withdrawn`

**Подробнее для заметок:**

Статусы вынесены в `PlatformStatuses.cs`. Они управляют доступностью действий, составом интерфейса и переходами между ролями. Это не display-метки, а основа жизненного цикла сущностей.

### 5.6. Как реализована модерация

**Коротко для слайда:**

- Куратор модерирует компании, публикации и кандидатов
- Поддержаны decision endpoints и сохранение причин revision/rejected

**Подробнее для заметок:**

Кураторский слой покрывает dashboard, списки, detail view, редактирование сущностей и принятие решений. Жалобы во frontend заведены как отдельный экран, но полноценный backend flow для жалоб в текущей ревизии не найден.

### 5.7. Как реализована верификация компаний

**Коротко для слайда:**

- Регистрация компании строится вокруг ИНН и Dadata
- После регистрации поддержана ручная document verification
- Без `approved` компания не создает новые возможности

**Подробнее для заметок:**

Регистрация работодателя использует проверку ИНН и сопоставление email/домена компании. Отдельный этап document verification собирает контактное лицо и файл проверки. До подтверждения компания не может открывать новый публикационный pipeline.

### 5.8. Как реализована приватность

**Коротко для слайда:**

- Кандидат настраивает visibility и audience
- Публичный профиль собирается с учетом relationship и настроек видимости

**Подробнее для заметок:**

Рабочая логика приватности кандидата опирается на `links/preferences` в профиле. На frontend это редактируется в privacy settings, на backend применяется при сборке публичного профиля. Поле `privacy_settings` в таблице есть, но основной runtime сейчас идет через `links`.

### 5.9. Как реализованы фильтрация и поиск

**Коротко для слайда:**

Home и catalog работают поверх реальных данных из `/opportunities`. При этом часть advanced filters и зарплатная сортировка пока выступают как подготовленная UI-структура, а не как завершенная бизнес-функция.

### 5.10. Как реализована карта и работа с геоданными

**Коротко для слайда:**

### 5.11. Какие сущности БД стоит показать на одном слайде

- `users` — базовая учетная запись, email, пароль, признаки верификации и основа авторизации.
- `applicant_profiles` — профиль соискателя, skills, links/preferences, moderation status, приватность.
- `employer_profiles` — профиль работодателя, ИНН, описание, verification status/method/data.
- `curator_profiles` — профиль куратора, включая `is_administrator`.
- `opportunities` — публикации всех типов, локация, координаты, контакты, media, moderation status.
- `applications` — отклики кандидатов со статусом, заметкой работодателя и `allow_peer_visibility`.
- `tags` — словарь тегов и связь many-to-many с возможностями.
- `contacts` — связи между пользователями, основа social-сценариев.
- `recommendations` — рекомендации и дополнительный слой карьерной персонализации.

Дополнительно в заметках можно упомянуть:

- `candidate_projects`
- `friend_requests`
- `candidate_project_invites`
- `opportunity_shares`
- `moderator_invitations`

## 6. Финальный пакет для сборки презентации

### 6.1. Финальное оглавление презентации

1. Трамплин: единая платформа карьерного старта
2. Как решение закрывает требования ТЗ
3. Главная страница: карта, список, поиск и фильтрация
4. Авторизация, роли и разграничение доступа
5. Кабинет соискателя: профиль и приватность
6. Кабинет соискателя: отклики, статусы и social context
7. Кабинет работодателя: профиль компании и верификация
8. Кабинет работодателя: создание и публикация возможностей
9. Кабинет работодателя: работа с откликами
10. Кабинет куратора: дашборд и очереди модерации
11. Куратор: проверка компаний, возможностей и пользователей
12. Frontend и backend архитектура
13. Модель данных, статусы и бизнес-связи
14. Код как доказательство и авторские решения
15. Репозиторий, тесты и видео-демо

### 6.2. Какие 5–7 экранов обязательны

- Главная страница с картой, поиском, фильтрами и карточками возможностей.
- Настройки приватности кандидата.
- Отклики кандидата со статусами.
- Верификация компании.
- Создание/редактирование возможности работодателем.
- Работа работодателя с откликами.
- Экран модерации компании или возможности у куратора.

### 6.3. Какие 5–8 кусков кода обязательны

- Role guard и redirect по роли.
- Backend JWT/cookie auth + policies по ролям.
- Сохранение privacy payload кандидата.
- Применение приватности в public profile API.
- Workflow document verification компании.
- Запрет публикации возможностей без подтвержденной компании.
- Apply flow кандидата с проверкой полноты профиля и `allow_peer_visibility`.
- Модерационное решение с сохранением причины `revision/rejected`.

### 6.4. Какие 3–5 авторских решений лучше всего продавать экспертам

- Единый discovery-сценарий через карту и список сразу для 4 типов возможностей.
- Двухступенчатая trust-model: верификация работодателя до публикации и модерация публикации до выхода в каталог.
- Приватность кандидата не только на уровне UI, но и на уровне API-выдачи.
- Social context вокруг отклика: контакты компании, люди из сети, видимые peers, пересылка возможностей.
- Регистрация работодателя по ИНН с проверкой через Dadata и invite-only onboarding модератора.

### 6.5. Что обязательно написать про репозиторий

- Прямую ссылку на репозиторий.
- Ветку или commit, по которому записано видео-демо.
- Краткое описание стека: React/Vite + ASP.NET Core + PostgreSQL.
- Указание, что README содержит локальный запуск и demo-аккаунты.
- Отдельную ремарку: работодатель логинится по ИНН, а не по email.
- Короткий блок про наличие frontend и backend tests.

### 6.6. Что обязательно показать в видео

- Главную страницу с картой, поиском и фильтрами.
- Разницу входа по ролям: кандидат / компания / куратор.
- Настройки приватности кандидата.
- Отклик кандидата и изменение его статуса.
- Верификацию компании и блокировку публикации без `approved`.
- Создание возможности работодателем и отправку на модерацию.
- Решение куратора по компании или публикации.
- Возврат результата в публичный каталог или кабинет.

### 6.7. Какие слабые места лучше не выносить в центр презентации

- Жалобы у куратора: интерфейс есть, но backend workflow не найден.
- Логи модератора: текущая реализация опирается на mock-данные.
- `tags-system` и `moderator settings`: scaffold-модули.
- Часть расширенных фильтров и зарплатная сортировка: интерфейс подготовлен, логика не завершена.
- Demo/fallback-состояния отдельных страниц не стоит выдавать за главный продуктовый proof.

### 6.8. Какие формулировки использовать, чтобы подчеркнуть сильные стороны

- «Реализован рабочий end-to-end сценарий от поиска возможности до модерации и обработки отклика».
- «Ключевая бизнес-логика подтверждена на трех уровнях: UI, API и модель данных».
- «Разграничение прав доступа обеспечено одновременно маршрутизацией frontend и policy-based авторизацией backend».
- «Приватность кандидата не декларативна: она влияет на состав публичных данных и social-context сценарии».
- «Верификация работодателя встроена в публикационный pipeline и напрямую влияет на доступ к созданию возможностей».
- «Статусы в проекте не декоративны, а управляют доступностью действий для всех ролей».
- «Частично готовые модули показаны честно как архитектурный задел, без подмены готовой функциональностью».
